= Bulkhead

For introduction, see xref:howto/bulkhead.adoc[How to Limit Concurrency].

== Description

If a guarded method is called by too many callers concurrently, the excess attempts will fail with `BulkheadException`.

If the guarded method is `@Asynchronous` or `@AsynchronousNonBlocking`, excess attempts are first put into a queue.
The queued attempts are executed later.
When the queue becomes full, excess attempts are rejected with `BulkheadException`.

=== Lifecycle

Bulkhead needs to maintain some state between invocations: the number of current executions and the queue of asynchronous executions.
This state is a singleton, irrespective of the lifecycle of the bean that uses the `@Bulkhead` annotation.

More specifically, the bulkhead state is uniquely identified by the combination of the bean class (`java.lang.Class`) and the method object (`java.lang.reflect.Method`) representing the guarded method.

For example, if there’s a guarded method `doWork` on a bean which is `@RequestScoped`, each request will have its own instance of the bean, but all invocations of `doWork` will share the same bulkhead state.

[[interactions]]
== Interactions with Other Strategies

See xref:howto/multiple.adoc[How to Use Multiple Strategies] for an overview of how fault tolerance strategies are nested.

If `@Fallback` is used with `@Bulkhead`, the fallback method or handler may be invoked if a `BulkheadException` is thrown, depending on the fallback configuration.

If `@Retry` is used with `@Bulkhead`, each retry attempt is processed by the bulkhead as an independent invocation.
If `BulkheadException` is thrown, the execution may be retried, depending on how retry is configured.

If `@CircuitBreaker` is used with `@Bulkhead`, the circuit breaker is checked before enforcing the concurrency limit.
If concurrency limiting results in `BulkheadException`, this may be counted as a failure, depending on how the circuit breaker is configured.

If `@RateLimit` is used with `@Bulkhead`, the rate limit is enforced before enforcing the concurrency limit.

If `@Timeout` is used with `@Bulkhead`, the timeout watcher is started before enforcing the concurrency limit.

For an asynchronous invocation, the time spent waiting in the bulkhead queue counts toward the timeout.
If the timeout elapses while the invocation is still waiting in the queue, the queued task is withdrawn before the caller observes the `TimeoutException`:

* it leaves the queue and releases the one capacity permit it acquired when it was accepted into the bulkhead (it never acquired a work permit, so the work semaphore is not touched);
* the guarded method is never invoked, so no side effects of an invocation the caller has already given up on happen later;
* a `FinishedWaiting` event is fired (balancing the earlier `StartedWaiting`), so `ft.bulkhead.executionsWaiting` decrements and one `ft.bulkhead.waitingDuration` sample is recorded, because the invocation really did wait; no `StartedRunning`/`FinishedRunning` events are fired;
* the withdrawal counts as the single `accepted` bulkhead decision and never adds a `rejected`.

A task that has already started running when the timeout elapses is not forcefully stopped; it runs to completion and releases its permits through the normal path.

The bulkhead learns about the timeout through an internal "invocation abandoned" event that the timeout strategy fires when the caller gives up on an asynchronous invocation.
This is a dedicated event rather than a handler on the timeout's own finished event, because it describes the caller's state (the result is no longer wanted) instead of one strategy's outcome, so other sources of abandonment besides a timeout can reuse the same mechanism.
Withdrawal and dequeue are adjudicated by a single atomic compare-and-swap on the task state: the thread that polls the task out of the queue switches it from waiting to running before invoking it, and the switch succeeding is the point of no return, after which a timeout can no longer withdraw the task.
Dequeue is chosen as the winning side so that the thread holding a work permit never ends up running a withdrawn task.
A thread that polls a task which was withdrawn in parallel releases the work permit it acquired and continues with the next queued task, instead of stopping with a free permit and a non-empty queue.
The capacity permit is released exactly once, by whichever side wins the state transition.
When `@Retry` is present, each attempt registers its own abandonment handler for its own bulkhead task; because handlers are append-only and never removed, a handler only ever acts on the task of the attempt that registered it, so two attempts can never release the same permit twice.

[[configuration]]
== Configuration

There are 2 configuration options, corresponding to the 2 members of the `@Bulkhead` annotation.

=== `value`

Type: `int`

Default: `10`

The concurrency limit.

=== `waitingTaskQueue`

Type: `int`

Default: `10`

The size of queue for excess attempts.
Only effective when the method is `@Asynchronous` or `@AsynchronousNonBlocking`.
See xref:reference/asynchronous.adoc[the Asynchronous Execution reference guide].
